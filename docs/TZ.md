## 1. Суть проекта

**Trend Pilot AI** — веб-платформа для селлеров, которая отвечает на вопрос: **«Что купить в Китае и продать на маркетплейсе, чтобы получить нужную маржу при моём бюджете?»**

Пользователь выбирает:
- где продавать (Kaspi, Ozon, Wildberries и др.),
- где закупать (Alibaba, 1688, Temu, AliExpress, Taobao и др.),
- бюджет,
- целевую кратность (2x / 3x / 5x / 10x),

и получает список категорий и конкретных товаров с реальной юнит-экономикой: закупочная цена, доставка, пошлины, комиссии, цена продажи, чистая маржа, спрос и конкуренция.

### Цели
1. Сократить время поиска товарных ниш с дней до минут.
2. Показывать **реальную** себестоимость (landed cost), а не просто цену на Alibaba.
3. Давать прозрачный расчёт: каждая цифра раскрывается до формулы и источника.
4. Работать только на реальных данных площадок: нет данных, значит «нет данных», без подстановок и выдуманных цифр (раздел 5.1).

### Не цели (v1)
- Не маркетплейс и не система заказа/оплаты закупок.
- Не автоматическая загрузка товаров на площадки продаж.
- Не бухгалтерия.

## 2. Пользователи и сценарии

**Персоны:** начинающий селлер (мало бюджета, нужна подсказка «с чего начать»), опытный селлер (ищет новые ниши, сравнивает площадки), байер/закупщик (проверяет конкретный товар).

**Ключевые сценарии:**
1. **Подбор по бюджету.** «У меня $3000, хочу продавать на Kaspi, закупать на 1688, минимум 3x» → список категорий и товаров, которые вписываются.
2. **Проверка товара.** Вставил ссылку/название → получил юнит-экономику по всем площадкам продаж.
3. **Сравнение площадок.** Один и тот же товар: где выгоднее продавать (Kaspi vs Ozon vs WB).
4. **Избранное и сравнение.** Сохранил товары в подборку, сравнил, выгрузил в Excel/PDF.
5. **Алерты.** Уведомление, когда у отслеживаемого товара маржа выросла/упала или спрос вырос.

## 3. Функциональные требования

### 3.1. Мастер подбора (главный экран)

Параметры фильтра:

| Параметр | Тип | Примечание |
|---|---|---|
| Площадки продажи | мультивыбор + режим «Все» (по умолчанию) | Kaspi, Ozon, Wildberries, + расширяемый список (Яндекс Маркет, Amazon и т.д.). В «Все» входят только площадки со статусом `active` в реестре источников (5.4) |
| Площадки закупки | мультивыбор + режим «Все» (по умолчанию) | Alibaba, 1688, AliExpress, Temu, Taobao, Pinduoduo, Made-in-China, DHgate. В «Все» входят только площадки со статусом `active` |
| Страна продажи | выбор | KZ и RU в v1, расширяемый список; влияет на комиссии, таможню, налоги и валюту |
| Бюджет | число + валюта | KZT / RUB / USD / CNY |
| Целевая маржа | пресеты 2x / 3x / 5x / 10x + свой ввод | Определение «x» — см. 4.2 |
| Категории | дерево, мультивыбор | Можно «все» |
| Модель логистики | FBO / FBS / DBS | У каждой площадки свои |
| Способ доставки из Китая | авто / карго / авиа / ж/д / море | Влияет на себестоимость |
| Доп. фильтры | | Мин. спрос, макс. конкуренция, вес/габариты, исключить хрупкое/сертифицируемое/запрещённое, мин. объём закупки (MOQ) |

**Правила выбора площадок:**
- Режим «Все» опрашивает все активные источники выбранной роли. Режим мультивыбора позволяет отметить любое подмножество.
- Площадка, у которой нет подключённого источника (статус `pending_registration`, `blocked` или `disabled`), отображается серым с причиной и датой ожидаемого подключения. Она не скрывается и не участвует в расчёте.
- Результат всегда показывает, по скольким площадкам из выбранных получены данные (см. 3.6).

### 3.2. Результат

Три уровня:
1. **Категории** — рейтинг по потенциальной марже, спросу, конкуренции, риску. Карточка: средняя кратность, медиана, число подходящих товаров.
2. **Товары в категории** — таблица с сортировкой/фильтрацией: фото, название, цена закупки, landed cost, цена продажи на каждой выбранной площадке, чистая прибыль с единицы, кратность, ROI, оценка спроса (продаж/мес), число конкурентов, риск-скор.
3. **Детали товара** — полный разбор юнит-экономики, график динамики цен и спроса, список поставщиков с рейтингами, альтернативные аналоги, предупреждения (сертификация, ограничения, брак/возвраты).

### 3.3. Бюджетный калькулятор
По выбранному бюджету система считает: сколько единиц можно закупить, ожидаемую выручку и прибыль, срок оборачиваемости, и **предлагает корзину из N товаров** (диверсификация), а не только один.

### 3.4. Юнит-экономика (редактируемая)
Пользователь может переопределить любой параметр (курс, стоимость доставки за кг, % выкупа, налог, рекламный бюджет) — результат пересчитывается мгновенно.

### 3.5. Прочее
- Избранное, подборки, заметки.
- Экспорт: XLSX, CSV, PDF.
- Алерты (email / Telegram).
- История запросов.
- Аккаунты, организации, тарифы и лимиты запросов (раздел 3.7).
- Языки интерфейса: RU, EN, KZ (все три в v1, перевод казахского проверяется вручную).
- Подключение собственных кабинетов продавца (Kaspi, Ozon, Wildberries) через токены с правами «только чтение» (5.3, слой A). Не входит в v1, добавляется позже.

### 3.6. Мульти-площадочная аналитика

- **Матрица «закупка × продажа».** Для каждого товара таблица: строки площадки закупки, столбцы площадки продажи, в ячейке кратность и чистая прибыль с единицы. Лучшая ячейка подсвечена.
- **Лучший канал закупки.** Минимальный landed cost с учётом MOQ, рейтинга и срока работы поставщика.
- **Лучший канал продажи.** Максимальная чистая прибыль с учётом спроса и конкуренции.
- **Аналитика закупок.** Цена по источникам и её разброс, динамика цены, число поставщиков, рейтинг и возраст поставщика.
- **Аналитика продаж.** Цена по площадкам, число продавцов, доля сильнейшего продавца, динамика отзывов и продаж (только если провайдер отдаёт продажи; иначе `no_data`).
- **Покрытие данных.** У каждого результата бейдж «данные с N из M площадок» и список площадок, по которым данных нет.
- **Расчёт асинхронный.** При выборе «Все» запросы идут по источникам параллельно, результаты появляются по мере готовности, прогресс виден по каждому источнику.

### 3.7. Модель продукта (SaaS)

Продукт предназначен для других селлеров, поэтому следующее закладывается с первого дня, потому что переделывать позже дорого.

- **Организации и пользователи.** Пользователь входит в одну или несколько организаций. Роли: владелец, участник, только просмотр.
- **Выдача доступа.** Самостоятельной регистрации нет. Администратор создаёт организацию и пользователя по запросу клиента в админке. Доступ передаётся одноразовой ссылкой-приглашением с ограниченным сроком действия, по которой пользователь сам задаёт пароль. Пароли в открытом виде не хранятся.
- **Изоляция данных.** Подборки, избранное, настройки, подключённые токены и расчёты принадлежат организации и недоступны другим. Правила доступа на уровне строк в базе, тесты на утечки между организациями.
- **Общие и частные данные.** Данные площадок и справочники общие для всех. Токены продавца (слой A), заметки, подборки и пользовательские переопределения частные.
- **Тарифы и лимиты.** Лимиты по тарифам: число расчётов, число подключённых кабинетов, число сохранённых подборок, доступ к режиму «Все», экспорт. Бесплатный пробный период (условия согласуются).
- **Оплата.** В v1 оплаты нет: закрытая бета, доступ выдаётся вручную по приглашениям. Организации, тарифы и лимиты закладываются в базу в Этапе 1. Провайдер оплаты для Казахстана и России выбирается позже (вопрос 28), подключение в Этапе 3.
- **Юридические документы.** Оферта, политика конфиденциальности, согласие на хранение токенов, дисклеймер «оценка не гарантирует прибыль». Нужна юридическая проверка для работы с пользователями из Казахстана и России.
- **Поддержка и безопасность.** Отзыв и удаление токенов по запросу, журнал действий, экспорт и удаление данных организации.

## 4. Модель расчёта (ядро продукта)

### 4.1. Формула

```
Landed cost (себестоимость с доставкой до склада/продавца) =
    цена закупки × курс
  + доставка внутри Китая
  + международная доставка (вес/объём × тариф)
  + таможенная пошлина + НДС (если применимо)
  + сертификация / маркировка (если нужна)
  + упаковка / фулфилмент
  + комиссия посредника/агента

Расходы продажи =
    комиссия маркетплейса (по категории)
  + логистика маркетплейса (хранение, приёмка, доставка клиенту)
  + эквайринг
  + рекламный бюджет (% от цены, настраиваемый)
  + возвраты/невыкуп (% × стоимость обратной логистики)
  + налог (режим: ИП упрощёнка / ОПН / иное — выбор)

Чистая прибыль с единицы = цена продажи − Landed cost − Расходы продажи
```

### 4.2. Определение «x» (кратность)
Решение принято (вопрос 1): по умолчанию **кратность = цена продажи / landed cost**, плюс отдельно показываем **чистую маржу %** и **ROI = прибыль / вложения**. Пользователь переключает, по какой метрике работает фильтр 2x/3x/5x/10x.

### 4.3. Справочники (редактируются админом)
- Комиссии площадок по категориям и странам.
- Тарифы логистики площадок (FBO/FBS) по габаритам.
- Тарифы карго по способам доставки. На старте справочник пуст; в расчёте без тарифа доставка получает `no_data`, пользователь может ввести свой тариф вручную в карточке товара.
- Таможенные ставки по кодам ТН ВЭД.
- Курсы валют (автообновление, источник — ЦБ/биржевой API) + буфер на волатильность.
- Налоговые режимы и ставки по странам. По умолчанию налог не учитывается, пользователь задаёт режим или ставку в настройках.

### 4.4. Прозрачность
Каждая цифра имеет «Почему так?» — раскрытие формулы, источник данных, дата актуальности. Показывать **диапазон** (пессимистично / реалистично / оптимистично), а не одно число.

## 5. Данные и источники

Это самая рискованная часть проекта. Цель: система работает только на реальных данных, без «воды», усреднённых значений и выдуманных цифр.

### 5.1. Принципы работы с данными

1. **Происхождение у каждой метрики.** Для любого значения в интерфейсе хранится: источник, способ получения (`api` / `provider` / `public_page` / `user_input` / `reference`), время получения и статус достоверности: `verified` (получено напрямую), `estimated` (рассчитано по формуле из ТЗ, показывается диапазоном), `no_data`.
2. **Нет данных, значит «нет данных».** Система не подставляет типичные, средние или сгенерированные значения. Оценка допустима только по формуле из раздела 4 и помечается `estimated`.
3. **Порог попадания в выдачу.** Товар показывается в результатах, только если есть минимум: закупочная цена из источника, цена продажи на выбранной площадке и хотя бы один сигнал спроса. Остальные уходят в раздел «Недостаточно данных» с указанием, чего не хватает.
4. **Спрос показываем честно.** Если провайдер не отдаёт продажи, спрос получает `no_data`, оценку по отзывам и рейтингу не строим. Отзывы, рейтинг и число продавцов показываются отдельно как факты со своим источником.
5. **Данные пользователя в приоритете.** Подключённые токены продавца (раздел 5.3, слой A) дают факты по комиссиям, тарифам и возвратам и перекрывают справочники.
6. **LLM не генерирует числа.** Языковая модель только объясняет и помогает сопоставлять товары (раздел 6).
7. **Приоритет при расхождении:** факт пользователя > официальный API > провайдер данных > публичная страница > справочник вручную. Если два источника расходятся больше чем на заданный порог, показываем оба значения и ставим предупреждение.

### 5.3. Стратегия получения данных (слои)

- **Слой A. Токены пользователя (BYO).** Пользователь подключает свои кабинеты Kaspi, Ozon, Wildberries с минимальными правами (read only, только нужные разделы). Токены хранятся зашифрованно, срок жизни отслеживается (напоминание за 14 дней до истечения). Даёт реальные комиссии, тарифы, возвраты и продажи по собственным товарам.
- **Слой B. Аккаунты платформы (наши).** Developer-аккаунты проекта на площадках, где это возможно (AliExpress Open Platform, Alibaba.com Open Platform, продавецкие кабинеты Kaspi, Ozon, Wildberries для справочных и тарифных методов). Оформление описано в Приложении A.
- **Слой C. Провайдеры данных.** Аналитика маркетплейсов (например, MPStats и аналоги, покрытие Kaspi проверить отдельно) и API-провайдеры китайских площадок (например, OT Commerce / OTAPI и аналоги). Выбор по пилоту: минимум два провайдера на каждый тип данных сравниваются по точности на эталонных товарах.
- **Слой D. Публичные страницы.** Сбор только того, что доступно без авторизации, с учётом условий использования площадок, `robots.txt` и лимитов. Запрещено обходить капчу и защиту от ботов. Включается только после юридической проверки.
- **Слой E. Справочники админа.** Комиссии, тарифы, ТН ВЭД, ставки карго. Резервный источник, всегда с датой актуальности.

Ядро и интерфейс не зависят от конкретного источника: каждый источник подключается через адаптер (`packages/adapters/<площадка>`) с единым контрактом.

### 5.4. Реестр источников

Таблица `data_sources` описывает каждый источник: площадка, роль (продажа / закупка), слой (A–E), метод, статус (`active` / `pending_registration` / `blocked` / `disabled`), лимиты запросов, стоимость запроса, срок действия токена, время последнего успешного обновления, доля успешных запросов. Админка показывает «здоровье» источников. В мастере подбора источник со статусом, отличным от `active`, показывается серым с причиной, а не скрывается молча.

### 5.5. Требования к слою данных

- Единый нормализованный формат товара вне зависимости от источника.
- Хранение сырых ответов источников (`raw`) для аудита и пересчёта при изменении формулы.
- Кеширование и периодическое обновление: цены ежедневно, спрос еженедельно, справочники по расписанию (настраивается).
- Метка свежести и статус достоверности у каждого значения.
- Очереди задач, ретраи с экспоненциальной паузой, учёт лимитов источников (например, ответы 429).
- Логирование и мониторинг сбоев адаптеров, алерты админу.
- Деградация: если источник недоступен, показываем последние известные данные с пометкой и датой.

### 5.8. Конвейер обработки данных

1. **Загрузка (ingestion).** Адаптеры по расписанию и по запросу обращаются к источникам с учётом лимитов (очередь, повторы с нарастающей паузой, обработка ответа 429). Каждый ответ сохраняется без изменений в `raw_responses`.
2. **Нормализация.** Приведение к единой схеме: валюты, единицы веса и объёма, категории, идентификаторы. Дубликаты объединяются. Записи, которые не проходят проверку (нет цены, нет валюты), отклоняются с причиной.
3. **Обогащение.** Сопоставление категорий источника с единым деревом категорий, привязка кода ТН ВЭД, расчёт объёмного веса.
4. **Сопоставление товаров (matching).** Поиск пары «товар закупки ↔ товар на площадке продажи»: кандидаты по эмбеддингам текста и изображений (`pgvector`), затем фильтры по характеристикам. Результат с `confidence`; низкая уверенность идёт в очередь ручной проверки.
5. **Метрики.** Статистика цен (медиана и квартили), конкуренция, динамика, риск-скор.
6. **Юнит-экономика.** Детерминированный расчёт в `packages/calc` по формуле раздела 4. Результаты сохраняются как снимки (`calculations`) с версией формулы и ссылками на исходные значения. Популярные комбинации фильтров рассчитываются заранее, пользовательские переопределения считаются по запросу.
7. **Выдача.** API читает готовые снимки и кеш, расчёт при подборе не ходит во внешние источники.
8. **Контроль качества.** Свежесть данных, покрытие по площадкам, аномалии (скачок цены, нулевая цена), здоровье источников. Проблемы попадают в админку и в алерты.

**Хранение:**
- сырые ответы: объектное хранилище или `jsonb` с партиями по дате;
- нормализованные данные и справочники: PostgreSQL;
- история цен и спроса: партиционированные таблицы по времени. Историю нужно копить с первого дня, потому что API отдают, как правило, только текущий снимок, и накопленная история сама становится ценностью продукта;
- векторы: `pgvector`;
- секреты и токены: зашифрованное хранилище, не в базе в открытом виде.

**Периодичность по умолчанию (настраивается):** цены ежедневно, спрос и конкуренция еженедельно, курсы раз в день, справочники по расписанию и по событию, токены пользователей: проверка срока ежедневно.

### 5.9. Нужен ли свой бэкенд

**Да, нужен.** Причины:
- **Секреты.** Токены Kaspi, Ozon, Wildberries и ключи developer-аккаунтов нельзя хранить и использовать в браузере. Запросы к большинству API с фронтенда не пройдут и по политикам доступа.
- **Лимиты и расписание.** Источники ограничивают частоту запросов. Нужны очереди, повторы и регулярные задачи, а не запросы «по клику» пользователя.
- **История.** Копить цены и спрос во времени может только собственное хранилище.
- **Обработка.** Нормализация, matching и массовый расчёт маржи по тысячам товаров не выполняются во фронтенде.
- **Стоимость.** Платные провайдеры данных нужно кешировать и лимитировать, иначе расходы выходят из-под контроля.
- **Соблюдение правил и аудит.** Журнал, откуда и когда получено каждое значение, возможен только на своей стороне.

**Состав бэкенда:**
1. **API-слой:** авторизация, фильтры, выдача, управление подключениями пользователей.
2. **Воркер:** адаптеры источников, очереди, расписание, обработка и расчёт. Работает отдельно от API, потому что задачи долгие.
3. **База данных и хранилище:** PostgreSQL, `pgvector`, объектное хранилище для сырых ответов.
4. **Админка:** реестр источников, справочники, очередь ручной проверки matching.

**Варианты:**
- **Рекомендуемый для MVP:** Next.js (фронтенд) + Supabase (PostgreSQL, авторизация, хранилище, правила доступа к строкам) + отдельный воркер на Node.js или Python с очередью (например, `pg-boss` на той же базе, чтобы не поднимать Redis сразу). Минимум инфраструктуры, быстро запускается. Облачные функции Supabase подходят для лёгких задач, долгие загрузки и расчёты идут в воркер.
- **Полноценный:** отдельный сервис API (NestJS или FastAPI) + PostgreSQL + Redis + воркеры. Переход возможен позже без смены схемы данных, если с самого начала держать адаптеры и ядро расчёта (`packages/adapters`, `packages/calc`) независимыми от способа развёртывания.
- **Не рекомендуется:** запросы к площадкам из браузера или только из серверных функций фронтенда без отдельного воркера.

## 6. AI-модули

1. **Product matching** — сопоставление товара на 1688/Alibaba с аналогами на Kaspi/Ozon/WB. Мультимодально: эмбеддинги изображений + текста, фильтры по характеристикам. Выдаёт `confidence`; при низкой уверенности — флаг «проверьте вручную».
2. **Trend score** — оценка динамики спроса (рост продаж, отзывов, поисковых запросов, сезонность).
3. **Competition score** — число продавцов, концентрация (доминирует ли 1–2 продавца), ценовой демпинг.
4. **Risk score** — сертификация, ограничения на ввоз, хрупкость/габариты, возвраты в категории, зависимость от бренда, подделки.
5. **Объяснение результата** — LLM-резюме на человеческом языке: «почему этот товар/категория в топе, чем рискуем». Строго на основе рассчитанных данных, без выдуманных цифр.
6. **AI-ассистент (чат)** — вопросы по результатам («покажи только то, что весит до 1 кг»), управляет фильтрами. v2.

**Принцип:** все финансовые расчёты — детерминированный код, не LLM. LLM только объясняет и помогает сопоставлять.

## 7. Нефункциональные требования

- Время ответа на фильтрацию по уже собранным данным: ≤ 2 сек. Мастер подбора (первый расчёт): ≤ 10 сек, с прогресс-индикатором.
- Адаптивность: десктоп (основной), планшет, мобильный.
- Безопасность: аутентификация, роли (user / admin), rate limit, защита от злоупотребления парсингом/лимитами, хранение секретов вне репозитория.
- Тестовое покрытие ядра расчёта юнит-экономики ≥ 90% (это сердце продукта).
- Логи, мониторинг, трекинг ошибок.
- i18n и мультивалютность с первого дня (не переделывать потом).
- Доступность: контраст AA, клавиатурная навигация.
- Токены и ключи API (пользователей и проекта): шифрование при хранении, отдельное хранилище секретов, маскирование в логах, отзыв и удаление по запросу пользователя.
- Аудит данных: у каждого значения хранится источник, время получения и статус достоверности; расчёт можно воспроизвести по сохранённым сырым ответам.

- **Frontend:** Next.js (App Router) + TypeScript, Tailwind CSS, shadcn/ui как база компонентов (кастомизировать под дизайн-систему проекта), TanStack Table для таблиц, Recharts/visx для графиков, Zustand/TanStack Query.

- **БД:** PostgreSQL (+ pgvector для эмбеддингов), Redis для кеша и очередей (BullMQ / Celery).
- **Воркеры:** адаптеры источников, пересчёт кеша, алерты.
- **AI:** Claude API для объяснений и ассистента; модель эмбеддингов для matching.
- **Хостинг:** Vercel / Railway / Supabase или VPS — по бюджету.
- **Структура репозитория:** монорепо `apps/web`, `apps/worker`, `packages/calc` (ядро расчёта, чистые функции, 100% тесты), `packages/adapters/*` (по одному на площадку).

### 8.1. Окружения

| Среда | Назначение | База данных | Источники данных |
|---|---|---|---|
| `local` | Разработка на компьютере | Локальная (Supabase CLI в Docker) | Моки и записанные ответы, при необходимости тестовые токены |
| `preview` | Одна на каждый pull request, для проверки фронтенда | Общая тестовая база | Моки и записанные ответы |
| `staging` | Предпродакшн, проверка релиза | Отдельный проект Supabase | Реальные источники с тестовыми токенами и ограниченными лимитами |
| `production` | Рабочая система | Отдельный проект Supabase | Реальные источники и боевые токены |

Правило: у каждой среды свои базы, токены и секреты. Боевые токены никогда не используются в `local`, `preview` и `staging`.

### 8.2. Локальная разработка и запуск

**Требования к компьютеру:** Node.js (актуальная LTS), `pnpm`, Docker, Supabase CLI. Если воркер на Python: Python 3.12+ и `uv` или `poetry`.

**Структура репозитория** (монорепо, `pnpm` workspaces + Turborepo):
`apps/web`, `apps/worker`, `packages/calc`, `packages/adapters/*`, `packages/db` (миграции и типы), `packages/ui` (дизайн-система), `fixtures/` (записанные ответы источников и эталонные кейсы).

**Команды (обязательны в `package.json` корня):**
- `pnpm setup`: установка зависимостей, создание `.env.local` из `.env.example`.
- `pnpm db:start`: локальный Supabase (Postgres, Auth, Storage, Studio) в Docker.
- `pnpm db:reset`: применение всех миграций и заполнение тестовыми данными.
- `pnpm dev`: параллельный запуск фронтенда, API и воркера.
- `pnpm test`: юнит-тесты и контрактные тесты адаптеров.
- `pnpm test:e2e`: сквозные тесты интерфейса.
- `pnpm lint`, `pnpm typecheck`, `pnpm build`.

**Критерий:** новый разработчик поднимает проект локально по `README` за 15 минут без боевых токенов и видит рабочий мастер подбора на тестовых данных.

**Работа без реальных токенов:**
- Каждый адаптер имеет три режима: `live` (реальный источник), `replay` (воспроизведение записанных ответов из `fixtures/`) и `mock` (синтетические данные). В `local` по умолчанию `replay`.
- Запись ответов (`record`) выполняется отдельной командой с тестовым токеном, секреты и персональные данные из записей удаляются.
- Для Wildberries использовать тестовый токен (в кабинете при создании токена есть режим Test scope / sandbox), для остальных источников, где песочницы нет, только `replay` и ограниченные тестовые вызовы в `staging`.
- Файл `.env.example` содержит все переменные без значений. Файлы `.env*` с секретами не коммитятся.

### 8.3. Тестирование

| Уровень | Что проверяет | Инструменты (предложение) | Где запускается |
|---|---|---|---|
| Юнит-тесты ядра | Расчёт юнит-экономики по эталонным кейсам `fixtures/calc-golden-cases.json`: на старте синтетические кейсы с независимо посчитанным ожидаемым результатом, по мере появления добавляются реальные кейсы заказчика; граничные случаи (нет данных, нулевые значения, разные валюты); покрытие ≥ 90% | Vitest (или pytest) | локально и CI |
| Контрактные тесты адаптеров | Что ответ источника по-прежнему соответствует ожидаемой схеме (ловит изменения API) | Vitest + записанные ответы, схемы Zod | локально и CI, плюс раз в сутки на `staging` против реального источника |
| Интеграционные тесты | Воркер + база: загрузка, нормализация, matching, сохранение снимков | Vitest/pytest + локальный Supabase | CI |
| Тесты качества данных | Свежесть, покрытие по площадкам, аномалии цен, отсутствие значений без источника | Запросы к базе по расписанию | `staging`, `production` |
| Сквозные тесты | Путь «площадки + бюджет + 3x → категории → товары → карточка», режим «Все», недоступная площадка серым | Playwright | CI на `preview` |
| Проверка дизайна | Соответствие дизайн-системе, поиск шаблонных ИИ-приёмов | Impeccable (`detect`, `audit`) | CI |
| Нагрузочные тесты | Поиск и выдача при тысячах товаров, время ответа ≤ 2 с | k6 | `staging` перед релизом |
| Тесты безопасности | Утечки секретов, права доступа к строкам, шифрование токенов | Проверка секретов в репозитории, тесты политик доступа | CI |

### 8.4. Развёртывание

Решение принято 18.10.2026: GitHub + Vercel + Supabase Cloud + Railway или Fly.io. Проекты `staging` и `production` создаются до первого деплоя.

| Компонент | Размещение (предложение для MVP) | Примечание |
|---|---|---|
| Фронтенд и API-слой (Next.js) | Vercel или аналог | Автоматический `preview` на каждый pull request |
| База данных, авторизация, хранилище | Supabase Cloud, отдельные проекты для `staging` и `production` | Регион выбрать с учётом задержек и требований к хранению персональных данных |
| Воркер (загрузка и обработка данных) | Docker-образ на Railway, Fly.io или VPS | Долгие задачи, расписание, очередь |
| Секреты | Секреты платформы развёртывания и Supabase Vault | В репозитории только `.env.example` |
| Мониторинг и ошибки | Sentry для ошибок, лог-сервис (Better Stack или Grafana), алерты админу | Метрики воркера: задачи, ошибки, свежесть данных |

Стоимость хостинга, провайдеров данных и LLM оценивается на Этапе 0 и согласуется до запуска.

**Важно:** запросы воркера к площадкам идут с IP облачного провайдера. Часть сайтов может блокировать такие адреса или ограничивать регион. Это одна из причин брать данные через официальные API и провайдеров, а не через сбор публичных страниц. Если сбор публичных страниц всё же включается, доступ организуется отдельным решением после юридической проверки.

### 8.5. CI/CD и релизы

1. Код в GitHub. Ветка `main` защищена, изменения только через pull request.
2. На каждый pull request автоматически: `lint`, `typecheck`, юнит-тесты, контрактные тесты, сборка, проверка миграций на чистой базе, `preview` для фронтенда, сквозные тесты и проверка дизайна.
3. Слияние в `main`: автоматическое развёртывание на `staging`, применение миграций, ночной прогон контрактных тестов против реальных источников.
4. Релиз в `production`: по ручному подтверждению владельца после проверки `staging`. Миграции базы применяются отдельным шагом и должны быть обратимыми или совместимыми с предыдущей версией.
5. Откат: возврат предыдущей версии фронтенда и воркера, миграции не удаляют данные без резервной копии.
6. Новые источники данных включаются флагами (`data_sources.status`) без повторного развёртывания.
7. Резервные копии базы по расписанию, проверка восстановления перед запуском `production`.

### 8.6. Порядок работы Claude Code

1. Создать монорепо и каркас команд из 8.2, убедиться, что `pnpm dev` поднимается с пустыми данными.
2. Настроить `CLAUDE.md` в корне репозитория: структура, команды, правила (формулы только в `packages/calc`, секреты не коммитить, каждое значение с источником).
3. Сначала написать и покрыть тестами `packages/calc` по эталонным кейсам. Если реальных кейсов заказчика нет, использовать синтетические: числа в них условные, помечены `synthetic: true`, не показываются в интерфейсе как рыночные данные и не попадают в справочники. Любое поле, которого нет во входных данных, даёт `no_data`, а не подставленное среднее.
4. Затем схема базы и миграции, адаптеры в режимах `replay` и `mock`, после этого интерфейс.
5. Реальные источники подключать по одному, после каждого: контрактные тесты, запись ответов, запись в реестр источников.

## 9. Дизайн и UI

### 9.1. Источник дизайн-системы
Дизайн-система берётся из **Impeccable** (https://github.com/pbakaus/impeccable), он установлен у заказчика. Claude Code не придумывает собственную систему и не использует стандартные темы библиотек компонентов «как есть». Порядок работы описан в 9.3.

### 9.2. Направление: минимализм с акцентными цветами

- **Минимализм.** Много воздуха, мало элементов, одна главная задача на экран. Структура держится на отступах и типографике, а не на рамках и тенях. Плотные таблицы допустимы только там, где пользователь сравнивает числа.
- **Цвет.** Нейтральная база (светлая тема по умолчанию, тёмная как вторая, переключатель в настройках) и акцентные цвета с чёткими ролями: основной акцент для действий и выбранных фильтров; шкала кратности 2x → 10x в акцентных цветах; отдельные цвета для статусов (риск, предупреждение, «нет данных», источник отключён). Цвет всегда несёт смысл и не используется для украшения.
- **Конкретные значения** (палитра, шрифты, радиусы, отступы) берутся из дизайн-системы, полученной через Impeccable, и фиксируются в design tokens. В этом ТЗ они не заданы и согласуются с заказчиком до верстки экранов.
- **Числа.** Табличные цифры, выравнивание по разряду, единицы и валюта всегда рядом со значением.
- **Запрещено (признаки шаблонного ИИ-дизайна):** градиентные заливки, одинаковые скруглённые карточки с мягкими тенями, фиолетово-синие градиенты, шаблонные hero-блоки, эмодзи вместо иконок, декоративные анимации.
- **Компоненты-приметы:** бейдж кратности (`3.4x`), спарклайны в ячейках таблицы, тепловая карта категорий, waterfall-диаграмма юнит-экономики (от цены продажи до чистой прибыли), статус источника данных (активен или серый с причиной), бейдж покрытия «данные с N из M площадок».
- **Анимации:** только функциональные (пересчёт чисел, раскрытие строк, подтверждение действия).

### 9.3. Порядок работы с дизайном (для Claude Code)
1. Проверить, что Impeccable установлен в проекте. Если нет, остановиться и попросить заказчика поставить его (`npx impeccable install`), без самостоятельной загрузки сторонних пакетов.
2. Запустить `/impeccable init` и зафиксировать контекст продукта: аудитория (селлеры маркетплейсов), главная задача (подбор товаров и расчёт маржи), тон (минимализм, акцентные цвета).
3. Сформировать дизайн-систему и design tokens командами Impeccable (подходящие команды перечислены в его README, например `typeset`, `colorize`, `layout`, `document`) и записать результат в один файл токенов и документацию проекта до начала верстки экранов.
4. Собрать UI-kit (кнопки, поля ввода, таблица, карточка товара, бейдж кратности, фильтры, waterfall-график, статусы источников) и показать заказчику на согласование.
5. Каждый экран пройти через `critique`, `audit` и `polish`. Проверку детектором (`npx impeccable detect src/`) включить в CI.
6. Skill `frontend-design` использовать как вспомогательный. При расхождении приоритет у Impeccable и согласованных токенов.
7. Референсы из Figma или Lovable использовать только если заказчик сам их предоставит.

## 13. Критерии приёмки MVP

1. Пользователь проходит путь «выбор площадок + бюджет + 3x → список категорий → товары → карточка» без ошибок.
2. Расчёт юнит-экономики на эталонных кейсах совпадает с независимо посчитанным ожидаемым результатом (синтетические кейсы на старте, реальные кейсы заказчика по мере появления). Перед открытием беты заказчик проверяет не менее 3 реальных товаров вручную.
3. Каждое значение в карточке раскрывается до формулы и источника с датой.
4. Смена курса или параметра пересчитывает результат ≤ 1 сек.
5. Дизайн соответствует разделу 9 и утверждённому UI-kit.
6. Падение одного адаптера данных не ломает приложение.
7. В интерфейсе нет ни одного значения без источника, времени получения и статуса достоверности. На контрольной выборке (пилот, 5.6) нет значений, взятых «из головы».
8. Режим «Все» и мультивыбор работают: результат показывает покрытие «N из M площадок», недоступные площадки видны серым с причиной.
9. При отсутствии данных система показывает «нет данных» или помещает товар в «Недостаточно данных», а не подставляет оценку.
10. Проект поднимается локально по `README` за 15 минут без боевых токенов (8.2); `pnpm test` проходит; на `preview` работает сквозной сценарий мастера подбора.
11. CI блокирует слияние при падении тестов, ошибках типов, проверки миграций или проверки дизайна (8.5).
12. Данные одной организации недоступны другой: автоматические тесты изоляции проходят (3.7).

## 14. Риски

| Риск | Митигация |
|---|---|
| Нет официального доступа к данным / блокировки при скрапинге | Адаптеры + лицензированные провайдеры; юридическая проверка |
| Неточность matching товаров | Показ confidence, ручная проверка, пользовательские правки |
| Устаревшие комиссии/тарифы | Справочники с датой, админка, ручное обновление + мониторинг изменений |
| Волатильность курса и логистики | Диапазоны, буфер, пересчёт по актуальному курсу |
| Завышенные ожидания «10x» | Показ рисков, реалистичного сценария и оговорка: «оценка, не гарантия прибыли» |
| Юридические ограничения (маркировка, сертификация, запрещённые товары) | Risk-скор и фильтры, дисклеймеры |
| Стоимость данных/LLM | Кеширование, лимиты по тарифам |
| Утечка данных между организациями (SaaS) | Правила доступа на уровне строк, автоматические тесты изоляции, ревью миграций |
| Приём оплаты и работа с пользователями из Казахстана и России | Юридическая проверка и выбор платёжных провайдеров до запуска оплаты (вопрос 28) |
| Ответственность за решения пользователей по закупкам | Оферта, дисклеймер «оценка не гарантирует прибыль», показ диапазонов и рисков |
| Официального доступа к 1688, Taobao, Temu нет без китайского юрлица или партнёрства | Провайдеры данных, китайский партнёр, поэтапное подключение (Приложение A) |
| Нет публичной аналитики рынка у Kaspi, Ozon и Wildberries в их официальных API | Гибрид: токены продавца, провайдеры аналитики, публичные страницы после юридической проверки (5.3) |
| Данные провайдеров и публичные страницы расходятся | Приоритет источников, показ обоих значений при расхождении, пилот на эталонных товарах |
| Токены пользователей истекают или отзываются | Отслеживание срока, напоминания, понятный статус подключения |
| Условия доступа к API меняются | Реестр источников, мониторинг ошибок адаптеров, проверка условий при каждой регистрации |
| Площадки закрывают данные для сторонних сервисов (пример: Wildberries, сентябрь 2025, по сообщению прессы) | Не строить ядро на одном источнике, копить собственную историю, держать провайдеров как запасной путь |
